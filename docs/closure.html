C5 - What to do better next project

Basis: C1, C2, _sessions/S1_build_lessons.md (L1 to L19), the S2 log in guide §231i (L20 to L24), runner logs.

What I did wrong

  1. Deferred the DataFactory sign-in in Discover (P5) while the owner was present. It became the single reason review test 3 needed a second session. Brief Rev 3 records the deferral.
  2. Did not ask at G1 who clicks Approve on test data. The owner delegated both approvals in one answer at the start of S2; asked at G1, the loop could have closed in S1.
  3. Designed the seed per row (GET then POST, about 1,280 calls at 1.6 s): it hit the 3000 s runner timeout (L7). $batch did 256 rows in 4.5 min (L11).
  4. Made the same format-then-encode bug twice (dv_build, flow_deploy, L6) before writing the lint.
  5. Skipped the S255 regenerate-and-diff before Publish, the second project in a row (P37 too). Run at Close: identical, but the rule is "before".
  6. Queued work on a runner without checking it was alive (S2): the lane 2 log had stopped at 02:37 MYT, seven hours earlier, with no exit line (L24).

What the owner did that cost time

  • The publish yes and the approvals waited for a new session. Neither needed new information; both were known at G2. One answer block at G2 ("approve test requests yourself; publish when the loop closes") would have removed the finish session's reason to exist.
  • The sign-in was left to "the next session" (handover S1 owner action 2) instead of being clicked while the Edge prompt was live.

What the owner did that was right and I did not

  • Waived the split and kept Build on Opus. The S2 read shows the conversation summary already reset cost per request (C6); a planned split would have bought the same reset with more handover work.
  • Delegated both approvals in one answer with the recommended option, which is exactly the decision shape the engine asks for.

C6 - Test one assumption: "a one-session project costs more per request as it grows, so split at a gate"

Basis: usage reads in _sessions/_cost/ (S1_G1, S1_G2, S1_G3, S2_G5) from the usage skill; P37 C8 for comparison. Cache read per request is the measurable proxy; turns and wall time per request are not available from the usage skill.

What the numbers say

  • Per-request cache read rose 19% from S1 A to S1 B, then fell 38% in S2 after the summary. The growth is real; the summary resets it.
  • A planned split at G2 would have bought the same reset the automatic summary gave, at the cost of a handover and a kickoff. P38 did not pay for the split and still got the reset.
  • The second session was not caused by cost or length at all. It was caused by owner-gated steps (C5).

Confounds

  • S2's work is lighter per call (short reads, browser text, small scripts) than S1 B's (builders, model deploys, long logs). Some of the drop is the work, not the reset.
  • The instructions share differs (S1 B 45.6%, S2 75.2%): S2 has fewer large tool results, so the fixed context is a larger part of a smaller total.
  • Two unrecorded stretches (C8) are missing from both sides.

Conclusion

The assumption is half right. Per-request cost grows within a segment (19% here), but the conversation summary resets it, so a gate split adds little for cost. The data does not settle whether the total for the project was lower or higher than a planned two-session run, because no planned-split control exists on the same work. Keep the owner's one-session default; split for owner availability, not for tokens.
